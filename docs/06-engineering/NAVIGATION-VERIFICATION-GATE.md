# Navigation Verification Gate

Every NoorPath slice that adds or changes a page, section, action target, breadcrumb, menu item, dashboard card, deep link or redirect must prove that the resulting experience is reachable and correctly linked before Product Owner approval.

This gate applies to customer, operator, agent, administrator and platform-administrator surfaces.

## Required outcomes

Each route or section must have exactly one recorded result:

- `PENDING` — implementation or verification has not yet completed. Permitted only while the slice remains in progress.
- `VERIFIED` — reached through the intended clickable navigation using the required identity, and the destination rendered the expected state.
- `BLOCKED_IDENTITY` — verification could not be completed because the required authenticated identity, membership, permission, tenant or external identity configuration was unavailable.
- `NOT_APPLICABLE` — the route is intentionally API-only, system-only or has no user navigation entry. The reason must be recorded.
- `FAILED` — the link, redirect, route, section anchor, permission handoff or destination did not work as intended.

A slice cannot be certified with any `PENDING` or `FAILED` navigation result.

`BLOCKED_IDENTITY` is not equivalent to verification. It is permitted only when the exact restriction, required identity/permission, attempted evidence and follow-up verification step are recorded in the slice navigation matrix and PR description. Product Owner approval must be informed of every remaining `BLOCKED_IDENTITY` item.

## Verification scope

For every generated or changed user-facing page or section, verify all applicable paths:

1. Primary entry point from the approved header, account shell, operator shell, administrator shell, dashboard card or package/journey flow.
2. Breadcrumb and back-navigation behavior.
3. Direct deep-link loading and refresh behavior.
4. Section links and in-page anchors, where present.
5. Desktop navigation.
6. Mobile navigation, including collapsed menus and responsive controls.
7. Authenticated authorized behavior.
8. Authenticated forbidden-role behavior and correct handoff guidance.
9. Unauthenticated behavior and return-to routing after sign-in.
10. Safe not-found behavior for foreign-account or foreign-operator resources.
11. Every button or link target generated by API projections.
12. No dead-end page: the user must have a clear next action or route back to the owning flow.

## Required evidence

Each slice must maintain a navigation matrix, normally at:

`docs/slices/<SLICE-ID>-NAVIGATION-VERIFICATION.md`

Each row records:

| Field | Required content |
| --- | --- |
| Surface | Customer, Operator, Agent, Admin or Platform Admin |
| Source | The page/section where navigation begins |
| Control | Exact visible link, button, card or redirect |
| Destination | Expected route and section |
| Identity | Required account, membership and permission |
| Result | `PENDING`, `VERIFIED`, `BLOCKED_IDENTITY`, `NOT_APPLICABLE` or `FAILED` |
| Evidence | Playwright test, screenshot, CI artifact or manual verification reference |
| Notes | Restriction, failure, follow-up owner and next action |

Automated rendered tests should click through from the real source whenever feasible. Tests that navigate directly to the destination do not, by themselves, prove that the page is linked.

## Certification rule

Before the `certify` label is applied:

- all new or changed routes and sections are present in the matrix;
- every expected user-facing destination has at least one working clickable entry point;
- direct route tests are supplemented by click-through tests;
- mobile and desktop navigation are both covered where navigation changes responsively;
- every identity-restricted gap is explicitly marked `BLOCKED_IDENTITY` rather than silently omitted;
- the PR body summarizes the matrix outcome and lists unresolved identity restrictions;
- no `PENDING` or `FAILED` result remains.

This gate does not authorize weakening authentication or permissions to make testing easier. Test identities must preserve the production role boundaries.
