# NoorPath V2 Data Architecture

Status: Draft baseline
Version: 0.1
Step: 12

## Purpose

This document defines NoorPath's logical and physical data architecture baseline for MVP: database ownership, schema boundaries, DbContext strategy, identifiers, transactions, concurrency, versioning, indexing, migrations, retention, backup and recovery expectations.

It builds on the Product/Domain baseline, State Machines, Integration Contracts, Security & Privacy Baseline and Architecture Baseline.

---

## 1. System of Record

PostgreSQL is the authoritative transactional system of record for structured NoorPath business data.

Private object storage is authoritative for document bytes and other large binary objects. PostgreSQL stores only the metadata and secure object references required by the Documents domain.

No reporting store, cache, search index, analytics platform or frontend state may become a competing source of truth.

---

## 2. Database Topology

MVP uses one managed PostgreSQL database per environment.

Within that database, logical capability ownership is expressed through PostgreSQL schemas where practical:

- identity
- operators
- catalogue
- pricing
- inventory
- traveller
- booking
- payments
- documents
- visa
- notifications
- support
- audit
- reporting
- platform_config

This is one database for operational simplicity, not one shared data model.

Each schema is owned by its corresponding module. Other modules do not write its tables directly.

---

## 3. DbContext Strategy

Preferred MVP direction: one EF Core DbContext per major module/persistence boundary rather than one global NoorPathDbContext.

Examples:

- IdentityDbContext
- OperatorsDbContext
- CatalogueDbContext
- PricingDbContext
- InventoryDbContext
- TravellerDbContext
- BookingDbContext
- PaymentsDbContext
- DocumentsDbContext
- VisaDbContext

Cross-cutting modules such as Audit, Notifications and Reporting may have their own contexts where persistence is required.

Rules:

1. A DbContext maps only tables owned by its module.
2. A module never imports another module's EF entity configuration as a navigation model.
3. Cross-module relationships use stable IDs/contracts rather than shared ORM graphs.
4. No generic repository/UoW abstraction is required over EF Core.
5. Transaction boundaries are module-local unless a specific same-database coordination pattern is explicitly approved.

Exact project/file topology remains an implementation ADR, but the ownership rule is baseline.

---

## 4. Identifier Strategy

All domain entities use opaque, stable identifiers.

Baseline recommendation:

- UUID/Guid-compatible identifiers generated by the application or database using a time-friendly strategy supported by the chosen platform/version where practical.
- Human-friendly references such as BookingReference are separate from primary identifiers.
- Public identifiers must not expose sequential tenant counts or encode security-sensitive meaning.

Rules:

- IDs are immutable.
- IDs do not encode mutable business attributes.
- BookingReference is not an authorization token.
- Cross-module contracts reference stable IDs, not database row addresses or natural keys.

---

## 5. Ownership and Foreign-Key Policy

Within a module schema, normal relational constraints and foreign keys are encouraged where they protect local invariants.

Across module schemas, cross-schema foreign keys should be used conservatively. The default is to store the external module's stable identifier without creating ORM navigation or direct write coupling.

Reason: module ownership and independent evolution are more important than creating a database-wide object graph.

Cross-module referential integrity is enforced by:

- synchronous owner validation where immediate validity is required,
- immutable snapshot/reference capture at commitment points,
- integration events/reconciliation where eventual consistency is appropriate,
- application and integration tests.

---

## 6. Transaction Boundaries

### Within one module

Use normal PostgreSQL ACID transactions for state changes that must commit atomically together.

Examples:

- Booking state change + Booking-owned snapshot changes
- Payment state + append-only ledger entry where those facts belong to the same Payments transaction
- Inventory hold acquisition + capacity accounting
- Domain state + module Outbox record

### Across modules

No distributed transaction is assumed.

A cross-module workflow is coordinated through:

1. synchronous contract calls when an immediate authoritative decision is required,
2. module-local commit,
3. transactional Outbox record when post-commit propagation is required,
4. retry-safe/idempotent consumers,
5. explicit reconciliation or compensation for partial failures.

No module is permitted to "solve" cross-module consistency by updating another module's tables inside its own transaction.

---

## 7. Concurrency Strategy

Concurrency is explicit where business races can corrupt truth.

### Inventory

Inventory hold/reservation is the highest concurrency hotspot.

Required outcomes:

- no known overselling under normal concurrent operations,
- atomic capacity check/acquire,
- idempotent hold-to-reservation conversion,
- deterministic expiry/release behaviour.

Implementation may use row locking, optimistic concurrency, atomic SQL updates or another PostgreSQL-safe strategy; the exact mechanism must be proven by integration/concurrency tests.

### Booking

Booking mutations use optimistic concurrency or equivalent protection so incompatible customer/admin/system transitions cannot silently overwrite each other.

### Payments

Provider webhook/event processing uses idempotency keys/unique provider references plus transactionally protected ledger/state updates.

### Documents

Review/resubmission uses version/submission identity checks so an obsolete document cannot be approved after a newer submission becomes current.

### Catalogue/Pricing

Published/versioned facts are immutable. Concurrency affects draft editing/publication transitions but cannot rewrite an already committed version.

---

## 8. Versioning and Historical Integrity

NoorPath distinguishes mutable working state from versioned/committed facts.

Versioned or immutable-after-publication concepts include:

- PackageVersion
- PriceVersion
- PaymentPlanDefinition
- DocumentRequirementSet
- policy definitions affecting customer commitments
- notification template versions where auditability matters

Booking captures immutable references/snapshots required to reproduce the customer agreement.

New versions never silently mutate existing bookings.

Financial ledger and protected audit evidence are append-oriented.

---

## 9. Money and Financial Data

Monetary values are stored using exact decimal/numeric semantics suitable for currency; floating-point types are prohibited for authoritative money calculations.

Every authoritative monetary fact includes an explicit currency.

Rules:

- PriceVersion defines commercial price facts.
- Booking preserves the agreed commercial obligation/snapshot.
- Payments owns settled/refunded financial facts.
- Outstanding balance is derived from agreed obligation and authoritative ledger facts.
- Settled financial records are never rewritten for convenience; corrections use compensating entries.

Database precision/scale is standardized per money type during physical schema design and tested for reconciliation.

---

## 10. Time, Dates and Timezones

Time semantics must be explicit.

Baseline:

- system event/audit timestamps stored as UTC instants,
- customer/business local dates remain domain dates where time-of-day is not meaningful,
- cutoff, quote expiry, hold expiry and payment deadlines include an explicit timezone/instant conversion rule,
- no business rule relies on server local timezone.

CreatedAt/UpdatedAt fields do not replace domain lifecycle/history where historical transitions matter.

---

## 11. Sensitive Data Storage

Data classification from the Security & Privacy Baseline governs persistence.

### Highly Sensitive

Examples: passport/identity document content, extracted document data, sensitive authentication material.

Rules:

- document bytes stay in private object storage,
- database stores opaque storage references and controlled metadata,
- secrets/tokens are not ordinary database business fields,
- logs, analytics and generic event payloads do not contain document content or unnecessary sensitive PII,
- lower environments do not use production PII as normal test data.

Field-level/application-level encryption may be added for specific highly sensitive structured attributes where threat analysis requires it; database-at-rest encryption alone is not assumed to solve all confidentiality risks.

---

## 12. Soft Delete, Archival and Deletion

A universal `IsDeleted` flag is prohibited as a default pattern.

Each domain chooses lifecycle semantics deliberately:

- bookings/payments/audit/publication history are retained according to business/legal obligations,
- cancellations change state rather than deleting commercial history,
- draft/transient records may be removable where no historical obligation exists,
- personal/document data follows explicit retention and deletion policy,
- deletion of identity documents must address object storage, metadata, derived/OCR data and backup-retention constraints.

Retention/deletion rules remain open until legal/privacy policy is finalized; implementation must not invent indefinite retention.

---

## 13. Indexing Strategy

Indexes are driven by known query patterns, constraints and production evidence.

Mandatory index categories include:

- primary keys
- unique business references where required
- foreign/reference IDs used heavily within a module
- operator/tenant scoping fields on operator-owned query paths
- lifecycle/status fields only when paired with meaningful query patterns
- departure/publication/date lookup paths for catalogue discovery
- booking owner/operator/reference lookup
- provider transaction/idempotency identifiers
- outbox pending/processing lookup

Rules:

- avoid indexing every column pre-emptively,
- composite index order follows actual filters/sorts,
- index changes are migration-reviewed,
- slow query telemetry feeds future optimisation.

---

## 14. Search and Reporting Data

MVP public catalogue search remains PostgreSQL-backed.

Search/read projections may denormalize data for efficient reads, but they are rebuildable and never writable domain truth.

Reporting/analytics projections are derived from authoritative capability states/events.

Dedicated search infrastructure, warehouse or read replicas require measured need and explicit architecture decisions.

---

## 15. Outbox Persistence

Reliable integration events are stored transactionally with the owning module's state change.

Preferred topology:

- each emitting module owns its outbox records/table or an explicitly partitioned module-aware outbox structure,
- event payload contains minimum required data,
- event ID is globally unique,
- occurrence time, type/version, correlation and processing state are recorded,
- no secrets/passport/document contents are placed in generic outbox payloads.

Worker processing supports:

- ordered handling only where a domain contract explicitly requires it,
- retry with backoff,
- poison/failure visibility,
- idempotent consumers,
- retention/cleanup after a governed period.

Exact shared-vs-per-module outbox table design remains an ADR.

---

## 16. Migration Ownership

Each module owns migrations for its schema/model.

EF Core remains the baseline migration mechanism.

Rules:

1. Migrations and model snapshots are generated by EF tooling, not hand-maintained substitutes.
2. CI runs pending-model-change validation.
3. A clean database must migrate to current successfully.
4. The previous supported release database must upgrade to current successfully.
5. Already-merged migration history is immutable except through an explicit exceptional repair decision.
6. Destructive changes require impact review, backup/recovery plan and typically expand -> migrate/backfill -> contract.
7. Data backfills are explicit, observable and retryable where necessary.
8. Production migration execution is automated/governed, not ad hoc developer workstation activity.

Migration ordering across module schemas must be deterministic at deployment time.

---

## 17. Schema Evolution Compatibility

Deployment must tolerate safe application/schema rollout sequencing.

Default strategy for risky changes:

1. Expand: add backward-compatible schema.
2. Deploy code capable of reading/writing compatible form.
3. Migrate/backfill data.
4. Verify production evidence.
5. Contract/remove old fields in a later controlled release.

Large table rewrites/locks must be reviewed for operational impact.

---

## 18. Backup and Restore Baseline

Production PostgreSQL and private object storage require managed backup/recovery capabilities.

Baseline requirements:

- automated backups enabled,
- point-in-time recovery capability for PostgreSQL where supported,
- backup encryption and restricted access,
- recovery procedure documented,
- restore tested periodically into an isolated environment,
- document-object recovery aligned with database metadata recovery so references do not silently diverge,
- RPO/RTO targets finalized in Reliability/Operations step.

A backup that has never been restored successfully is not accepted as recovery evidence.

---

## 19. Data Residency and Environment Isolation

Exact production region/residency remains an architecture/privacy ADR.

Regardless of region:

- each environment has isolated databases/storage/secrets,
- PROD data is not routinely copied to DEV/CI/LOCAL,
- test fixtures use synthetic/redacted data,
- staging must reproduce schema/migration/scale characteristics sufficiently for meaningful validation without using unrestricted production PII.

---

## 20. Data Access Patterns

Commands operate through the owning module's application/domain boundary.

Queries may use efficient read models/projections within ownership rules.

Rules:

- no controller directly mutates tables,
- no module performs direct SQL against another module's private schema as a shortcut,
- read composition across capabilities happens through explicit contracts/projections,
- direct EF Core/Dapper/native SQL inside a module is allowed where justified; technology choice does not override module ownership,
- N+1 and unbounded queries are release concerns, not deferred indefinitely.

---

## 21. Data Quality and Constraints

Database constraints complement domain validation.

Use database-level guarantees for facts such as:

- required non-null relationships within a module,
- uniqueness of business/provider/idempotency references where required,
- valid numeric ranges where universally true,
- optimistic concurrency/version tokens where selected,
- check constraints where they encode stable invariants and do not duplicate volatile policy.

Operator-configurable or evolving policies belong in domain/application logic/versioned policy rather than brittle database checks.

---

## 22. Data Observability

Operational telemetry should include:

- database connection saturation
- query latency and slow-query evidence
- lock/deadlock events
- migration duration/failure
- outbox backlog/oldest age
- payment reconciliation backlog
- inventory contention/failure metrics
- document metadata/storage reconciliation failures
- backup/restore status

Sensitive query parameters/data are not logged indiscriminately.

---

## 23. Data Architecture Tests

Before affected slices are Done, tests should cover where applicable:

- module ownership/dependency rules
- real PostgreSQL integration behaviour
- unique/constraint behaviour
- optimistic concurrency conflicts
- inventory concurrency/oversell prevention
- payment idempotency
- document submission version race
- migration from empty database
- upgrade from previous release schema
- outbox atomic persistence with domain state
- cross-tenant query isolation
- financial reconciliation arithmetic

---

## 24. Explicit MVP Non-Goals

Not baseline for MVP:

- database-per-module deployment
- sharding
- multi-region active-active writes
- event sourcing
- universal soft delete
- global shared EF model
- distributed cache as source of truth
- Elasticsearch/OpenSearch as source of truth
- cross-module ORM navigation graphs
- manual production schema edits

---

## 25. Open Data Decisions

Still to freeze in subsequent ADR/Operations work:

1. Exact PostgreSQL version/managed-service SKU and production region.
2. Final per-module DbContext/project arrangement.
3. Shared versus per-module Outbox table topology.
4. Exact UUID/time-sortable ID implementation.
5. Physical money precision/scale standard.
6. Exact catalogue search/index strategy after query design.
7. Document metadata encryption requirements beyond platform encryption.
8. Retention/deletion schedules for each data class.
9. Production backup retention, RPO and RTO.
10. Whether any cross-schema foreign keys are justified.
11. Long-term reporting/analytics store after MVP evidence.
12. Database connection-pool and capacity thresholds after load testing.

## Freeze Rule

No implementation may create shared-table shortcuts, cross-module writes, mutable financial history, public document storage references, unmanaged migration history or a competing data source without an explicit architecture/data decision and impact analysis.
